# CoinMaster — единое ТЗ для Codex
Версия: 1.0 · 19.09.2026 · Репозиторий: https://github.com/VF78/coinmaster

## 0. Задача и границы

Построить на NautilusTrader систему BTC/SOL: загрузка данных → backtest → подбор параметров → paper → развёртывание для live. Сохранить полезный интерфейс CoinMaster. Этот файл самодостаточен: старые архивы, отчёты и историю чата читать не требуется.

**Цель — максимальный конечный TOTAL = ACTIVE + RESERVE после всех издержек.** Начальный TOTAL — 10 000 USDT-equivalent. ACTIVE — доступное обеспечение и нереализованный PnL; RESERVE — средства вне обеспечения торгового аккаунта. Не подменять цель Sharpe, сохранностью ACTIVE, простотой стратегии, ограничением DD или числа ликвидаций. Ликвидация и рестарт — денежные события модели, не автоматический дисквалифицирующий признак. Биржевые ограничения, достоверность данных и правильность расчётов обязательны.

Передаётся **исследовательский кандидат `btc_sol_wave_overlay_v1`**, а не проверенная live-стратегия. Биржа-победитель ещё не установлена. Численные результаты старых приближённых расчётов не являются критериями приёмки. Сначала реализовать параметры ниже без изменения правил; затем оптимизировать на проверенной модели.

В целевом запуске: один Nautilus-исполнитель, одна биржа, один выделенный аккаунт/субаккаунт на экземпляр. BTC и SOL находятся на одной бирже. Freqtrade и старые JS-исполнители не участвуют. В MVP не входят funding-арбитраж, intraday, другие стратегии, LLM-сигналы, новости и Radar. **Funding по открытым perpetual-позициям учитывается обязательно.**

Изменения делать в отдельной Git-ветке, не уничтожать старые исходники и пользовательские изменения. Реальные сделки, переводы, takeover позиций и переключение работающего production требуют отдельного разрешения владельца. Без него результат проекта — готовая система в paper-режиме и инструкция активации.

## 3. Математика и правила стратегии

### 3.1. Данные и признаки

Все времена UTC. Хранить `open_time`, `close_time`, `available_at`. Сигнал использует только закрытые и уже доступные бары; исполнение строго после решения. EMA берётся по close, рекурсивно с α=2/22, `adjust=False`; исходное значение — первый доступный close. Для сопоставимости фиксировать начало ряда и warmup.

Для закрытого дня t, где B — BTC close, S — SOL close:

```text
side_t = +1, если B_t > EMA21_t; иначе −1 (равенство = short).
rB_t = ln(B_t / B_(t−1)); rS_t = ln(S_t / S_(t−1)).
beta_t = Cov(rS, rB) / Var(rB), последние 270 закрытых дневных доходностей.
R_t = ln(S_t / S_(t−65)) − beta_t × ln(B_t / B_(t−65)).
mu_t, sigma_t = mean и population std последних 180 R, ИСКЛЮЧАЯ R_t.
z_t = (R_t − mu_t) / sigma_t.
z_signed_t = episode_side × z_t.
```

При недостатке истории, NaN, нулевой дисперсии или beta вне `(0.2, 4)` не создавать новый риск; выходы продолжаются. Не подставлять beta=1. После первого SOL-fill фиксировать **sigma сигнального дня** для этой открытой SOL-позиции. R и mu продолжают обновляться: последующие входы/выходы используют `(R_t−mu_t)/sigma_fixed`. При полном закрытии SOL фиксация снимается. **Beta для расчёта сигналов динамическая; beta для размеров эпизода фиксированная** — не перепутать.

### 3.2. Статистика волн

Статистические BTC-волны определяются сменой дневного режима, независимо от фактических стопов/переоткрытий стратегии. Начало волны — следующий дневной open после сигнала смены режима. Конец — перед следующим исполнением смены режима. Сохранять только завершённые и уже известные волны.

`MFE = max(0, max(side × (close / wave_entry_open − 1)))` по дневным close внутри волны. Для каждого направления брать волны, завершившиеся за предыдущие 730 дней; минимум 8; нули включать. Квантили — линейная интерполяция. Нулевой уровень не является отсутствующим значением. На входе фиксировать три уровня; не пересчитывать их по будущей истории.

### 3.3. Начало эпизода

Когда аккаунт flat и не заблокирован, после закрытого дня создать BTC-вход по `side_t`:

`N_requested = min(9 × ACTIVE_marked, max_parent_notional)`.

Пройти preflight маржи/ликвидности/точностей. По фактическим fills зафиксировать `episode_id`, сторону, VWAP входа BTC, первоначальное количество `Q_B0`, `ACTIVE_entry`, `beta_entry` сигнального дня и `H = N_B_filled / beta_entry`. SOL пока отсутствует. Не считать заявку исполненной по acknowledgement.

Частично исполненный BTC-parent завершается подтверждённой отменой остатка; размеры эпизода фиксируются по фактическому исполнению. Новые решения по нему — после завершения этого parent.

### 3.4. BTC-тейки и SOL-доборы

На закрытии дня `f = episode_side × (B_close / BTC_entry_VWAP − 1)`.

При `f >= wave_level[j]` создать reduce-only BTC-выход на 15/25/35% **первоначального** количества, каждый уровень один раз. Несколько уровней могут сработать вместе; суммарный выход не больше остатка. Это тейки по дневному закрытию с последующим исполнением, НЕ исполнение задним числом на high/low дня.

После фактического достижения/исполнения BTC-уровня j соответствующее право SOL-добора сохраняется до конца эпизода. Если `z_signed >= [1.25, 2.50, 3.75][j]`, открыть SOL против BTC размером `H × [1, 1.5, 2][j]`, ограниченным cap и маржой. Каждый j — не больше одного parent-добора за эпизод.

Сначала исполнить все BTC-сокращения, получить фактические fills/маржу, затем проверять SOL. H не уменьшается вслед за BTC-тейками. При нехватке маржи default — reject, повторная оценка не раньше следующего дневного решения. Частичный fill завершает уровень в фактически исполненном объёме после отмены остатка; отменённую разницу не превращать в новый полный добор. `clip` реализовать как отдельную политику с отдельным config hash.

### 3.5. SOL-выходы

Для текущей SOL-позиции при `z_signed <= 0.375` закрыть 50% её фактического количества. После исполнения половины и **не раньше следующего дневного решения**, при `z_signed <= 0.125` закрыть остаток. Если сразу выполнены оба условия — не закрывать 100% вместо исследуемой последовательности.

Через 14 дней от первого fill текущей SOL-позиции закрыть её полностью на ближайшем дневном решении. Таймер не сдвигается из-за добора. Новый SOL-добор сбрасывает флаг половинного выхода, но не реализованный PnL, не таймер и не уже замороженную sigma. После полного выхода очистить sigma/таймер. Неиспользованные уровни могут сработать позднее в том же BTC-эпизоде.

В дневном цикле без глобального закрытия порядок: BTC reductions → SOL additions → SOL partial/timeout exits. При необходимости изменить порядок создать новую версию, а не молча улучшать тест.

### 3.6. Завершение эпизода и деньги

Смена режима закрывает все оставшиеся позиции. Хранить `best_f = max(0, все закрытые f эпизода)`; если `best_f > 0.03` и `f <= best_f−0.03`, закрыть эпизод. Это **отступ 3 процентных пункта по дневным close**, не трейлинг 3% от цены пика и не непрерывный биржевой стоп.

Ликвидация и фактические mark-события обрабатываются раньше ещё не исполнимого добровольного выхода. Следующий эпизод возможен и в том же режиме; не добавлять правило «только после нового EMA-cross». При смене режима разрешён новый вход после сверки полного закрытия старой группы. После прочих дневных выходов — не раньше следующего дневного решения; после ликвидации — только по политике восстановления.

Резервная политика параметризована, но в исходном кандидате выключена. При включении: только flat и без открывающих ордеров; если ACTIVE >= base × multiple, перевести fraction от ACTIVE вне cross collateral. Базу обновить **после подтверждения** перевода. Пока перевод pending, не считать сумму защищённой и не открывать новую позицию на неё.

После ликвидации отменить открывающие остатки, сверить и завершить обе ноги; сохранить фактический остаток. Пополнить ACTIVE из RESERVE до первоначального seed, либо на доступную сумму. Без RESERVE default — остановка новых входов даже при положительном остатке; продолжение на остатке — отдельный исследовательский вариант. Внутренние переводы не меняют TOTAL; внешние пополнения не являются доходностью.

## 4. Реальное обеспечение, исполнение и восстановление

### Профиль биржи

Для BTC и SOL получить и сохранить raw snapshot: instrument ID, settlement currency, qty/tick precision, min notional, max child order, position/open-interest limits, leverage и все ступени IM/MM с deductions, режим обеспечения, расписание funding, тариф аккаунта и дату применимости. Снимок имеет источник, время, hash и список неизвестных полей. Публичных максимальных плеч недостаточно; текущие таблицы не выдавать за исторические.

Запросы P0 — только чтение. Отсутствие account keys не блокирует локальные тесты, но соответствующие параметры помечаются UNVERIFIED. Bybit SOL tiers не заменять предположением 50×. HL USDC и исходный USDT учитывать через реальную конверсию/расходы, не как бесплатный перевод 1:1.

### Preflight каждого увеличения

```text
IM_total = сумма биржевых IM позиций и risk-increasing pending orders
           + предусмотренные биржей расходы/резервы.
MM_total = сумма требований ступеней с deductions и корректировками venue.
Equity_after_entry_costs >= IM_after_order + явный allocation buffer.
Gross_after_order <= configured_max_gross_to_active × ACTIVE_after_costs.
```

Цена для маржи — по правилам venue, ликвидационный триггер — mark. Пересчитывать ступень при движении цены, не только после fill. Не вычитать SOL-IM из BTC-IM из-за противоположных направлений. PnL ног входит в equity один раз. Закрывающая комиссия/буфер не должны становиться второй фактически списанной комиссией или подменять официальный MM.

`future_sol_margin_fraction` резервирует часть будущей SOL-IM **внутри ACTIVE**. Это не RESERVE. Оценивать по сумме плановых SOL-позиций и ступеням; будущие BTC-тейки не считать заранее исполненными. При полном резервировании первоначальный BTC-вход может оказаться недоступен — default reject, не скрытый resize.

### Ордерный цикл

Один parent intent с ключом `(account, strategy_version, episode, action, level)`; qty/цена — Decimal и округление по метаданным. Native адаптер отправляет ордера. IOC-limit с явным price bound либо поддержанный market с оценкой impact; модель должна учитывать выбранный тип. Не строить новый exchange SDK для исполнения.

Полный parent-cap не отменяет лимит дочернего ордера или совокупной позиции. В первой версии parent, превышающий допустимый безопасно моделируемый размер child, не исполнять фиктивным мгновенным batch. Разбиение вводить только при необходимости, последовательно, со свежей ценой, частичными fills и лимитом общего времени/стоимости.

При timeout сначала сверить client ID, open orders и recent fills; не повторять полный ордер вслепую. Каждое исполнение/funding/transfer учитывать один раз по устойчивому ID. Funding начислять в фактический момент на реально открытую позицию, включая отрицательные ставки; оценка следующего funding не является начислением.

SQLite WAL: immutable configs/runs, commands, intents, executions, funding_events, transfers, ledger_entries, snapshots, health. Уникальные индексы на venue/account/execution_id и client_order_id. Короткие транзакции; API пишет команды/задания, worker — торговые события. Единственный источник расчёта торгового PnL — фактические события native/venue, не независимый счётчик UI.

После перезапуска загрузить snapshot+journal и выполнить read-only сверку balances/positions/orders/fills/funding через native API. Неизвестные позиции не присваивать и не закрывать автоматически. При неоднозначности — MANAGE_ONLY, без нового риска. Потеря API/UI не должна остановить worker. При неизвестных tiers, stale data, конфликте второго исполнителя запрещаются увеличения, но не блокируются необходимые закрытия.

## 5. Проверки, подбор и отчёт

Сначала получить данные, затем сравнивать биржи. Нужны 24 полных месяца с единым cutoff и warmup не менее 730 дней: реальные цены контрактов, mark и состоявшийся funding каждой площадки, метаданные и тарифы. Предпочтительны 1m/trades/BBO для исполнения; более грубое разрешение обозначать. Разные источники и spot/futures не смешивать без proxy-метки. Raw неизменяемый, normalized Parquet с manifest/hash; пропуски не превращать в нулевой funding или вымышленные свечи.

Одна domain-реализация и один Nautilus lifecycle для backtest/paper/live. До массового подбора проверить, реально ли выбранная версия проводит funding и корректные изменения маржи через native account. Если нет — небольшой протестированный SimulationModule/поддержанное расширение; не вычислять альтернативную прибыль постфактум и не писать второй симулятор.

Обязательные тесты:
- Нет future data: добавление будущих баров не изменяет прошлые признаки/сигналы; разные UTC/DST настройки дают тот же результат.
- Beta, z с исключением текущего значения, fixed sigma, линейные квантили и нулевые волны покрыты ручными fixtures.
- Для условного BTC 80k/40 и SOL 80k/20 требуется суммарно 6k IM, не 0; параметры fixture не заменяют production profile.
- Все BTC TP считаются от initial qty; частичный fill не освобождает полную ожидаемую маржу; TP/add/half-exit не дублируются.
- Три SOL-add не считаются обеспеченными стартовым балансом автоматически; rejected/clip/partial ветки различимы.
- Long/short и знак funding; событие рядом со входом; повторное событие после reconnect; отрицательные ставки.
- Tier crossing, mark vs last, комиссия, округление, гэп и отсутствие ликвидности; недоступный стоп не исполняется по желаемой цене.
- TOTAL = старт + realized + unrealized − расходы + signed funding; переводы не создают прибыль, reserve вне залога.
- SIGKILL после отправки до ACK и повторный websocket fill не создают двойную позицию/доход. Ликвидация одной ноги запускает сверку всей группы.
- На конце теста все остатки закрываются с расходами, и отдельно сохраняется конечная ликвидируемая стоимость.

Подбор: фиксированный seed, сохранение всех попыток и неактивных параметров. После корректного базового native-прогона сравнить Bybit/HL на одинаковом начальном TOTAL и общем периоде. Вокруг лучшего сочетания — шаги 5–10% для размеров, 0.0625–0.125 для z, ±5–15 дней для окон. Сравнить load, SOL sizes, уровни волн/тейков, exits, timeout/trail, резерв, earmark, reject/clip и исполнение. **Fees, ликвидность, доступное плечо и исторические данные не подбирать ради удобного ROI.**

Основной рейтинг — terminal TOTAL; полный максимум помечать hindsight. Рядом проверять независимые свежие старты, последовательные train/test окна, расходы/задержки/ликвидность. Не объявлять уже просмотренный период нетронутым OOS. Отрицательные результаты и ликвидации сохранять, а не исключать скрытым фильтром.

На каждый запуск: `config/profile/data/code hashes`, summary, equity ACTIVE/RESERVE/TOTAL, executions, episodes, funding, fees/slippage, transfers, rejects, monthly returns, tests/model limitations. Выбор кандидата владельцем для live — отдельно от выбора максимума оптимизатором.

## 6. Минимальный интерфейс и API

**Strategy:** параметры кандидата, биржа/аккаунт, preview реального BTC-входа и трёх SOL-добавлений, IM/MM, свободная маржа; requested vs allowed. Подпись cap — «максимум заявки при достаточном обеспечении», не стартовый размер.

**Research:** запуск/отмена заданий, прогресс, сравнение terminal TOTAL, результаты/все попытки, фильтры venue и evidence. Видны MISSING_FUNDING, PROXY_PRICES, UNKNOWN_TIERS. Большие CSV/логи подгружаются по запросу.

**Runtime:** обе ноги, ордера/частичные исполнения, ACTIVE/RESERVE/TOTAL, маржа, журнал, здоровье данных и сверки. Раздельные команды pause-new-entries и flatten; пауза не прекращает сопровождение.

API `/api/v1`: health, venue-profiles, immutable configurations, runs (backtest/paper, status/cancel/report), runtime, events с cursor, commands с idempotency key, отдельная live-activation. Типы генерировать из OpenAPI; деньги передавать decimal strings. Изменённый config не меняет работающий эпизод; применять после flat или через явно версионированный план миграции.

HTTPS и аутентификация, проверка origin/CSRF при cookie-сессиях; административные команды не публиковать без защиты. API binds localhost/private network. Секреты только в защищённом окружении worker, не в UI/SQLite-конфигах/логах/промптах. Bybit trade-only key; HL agent wallet и реальный account address; права переводов проверяются отдельно. Никаких автоматических mainnet-депозитов ради testnet faucet.

## 7. План реализации без лишнего контекста

| Этап | Что сделать | Критерий завершения |
|---|---|---|
| P0 | Проверить HEAD, структуру и активные сервисы без изменения production. Зафиксировать pin, получить публичные профили обеих бирж и покрытие данных. | Короткий список reuse/gaps, lock/install, raw snapshots, manifest; неизвестные параметры явно обозначены. |
| P1 | Native вертикальный срез: BTC+SOL, одна ручная группа, partial reduce/add, funding, margin и итоговый ledger. | Результат равен ручным денежным fixtures; нет второго backtest engine. |
| P2 | Реализовать всю domain-логику раздела 3 и state machine, исходный config. | Детерминированные replay/no-lookahead/quantity tests; журнал всех действий. |
| P3 | Подготовить реальные/явно маркированные данные, native baseline, сравнение площадок и мелкую оптимизацию. | Полные отчёты с provenance и объяснением расхождений; никакой подгонки к старым процентам. |
| P4 | Paper, persistent intents, reconciliation, retries, частичные fills, аварии, резерв. | Crash/restart-тесты проходят; нет дублирования денег/ордеров; неизвестное состояние блокирует только новый риск. |
| P5 | Три страницы с прежними UI-компонентами и узкий API. | GUI показывает фактическое состояние, не вызывает legacy execution; UI недоступность не останавливает trader. |
| P6 | Воспроизводимое развёртывание, backup/restore, мониторинг, инструкция cutover. | Paper smoke на VPS при предоставленном доступе; live только после отдельного разрешения. |

Работать последовательно до ближайшего реально проверенного результата. Не завершать каждую задачу только планом и не запрашивать повторное разрешение на обычные локальные действия внутри ТЗ. Останавливаться из-за отсутствующих секретов, доступа, необратимого решения или реального blocker; независимые локальные задачи продолжать. Неполученную историю не объявлять готовой проверкой.

Один ведущий исполнитель отвечает за domain/ордера/деньги. Второй после утверждения интерфейсов может заниматься UI/импортом. Не редактировать state machine параллельно двумя агентами. Для денежных инвариантов отдельное ревью; для типовых UI/служебных задач — минимально достаточная модель. Модели AI не встраивать в торговую логику.

Создать только краткий `TASK_STATE.md`: текущий этап, принятые решения, файлы, выполненные команды/тесты, blockers, следующий шаг. На задачу читать нужный раздел ТЗ и затронутые файлы; не загружать целиком репозиторий/данные/логи, не делать десятки повторяющих ТЗ документов. Один checkpoint commit на завершённый этап; отчёт ≤15 строк. Изменение торговых правил — новая версия кандидата и отдельный commit от рефакторинга.

## 8. Развёртывание и завершение

Выбрать один способ deployment: существующий подход VPS, если пригоден; иначе Docker Compose с сервисами api/trader и разовым research-job. Не поддерживать одновременно альтернативные systemd/Compose реализации. Frontend собрать статически, backend запускать с lockfile; NTP, TLS, healthchecks, restart policy, CPU/RAM-ограничения research. Для старта ориентир 4–8 vCPU/16 GB RAM без гарантии потребления; тяжёлый перебор не запускать в live event loop.

SQLite online backup, immutable конфиги/manifest, проверенный restore. Logs с ротацией и редактированием секретов. Наблюдать data age, clock skew, rejects, free IM, MM coverage, funding gaps, unmatched orders/fills, reserve pending, slippage. Алерты без LLM в аварийном контуре.

Поставить в репозиторий код, тесты, lock, миграции, `.env.example` без секретов, Compose/существующие unit scripts, пример paper-config, CLI/Makefile-команды install/test/backtest/paper/doctor/backup и короткий runbook. Команды должны быть реально выполнены в доступной среде; отсутствие VPS отметить, а не заявлять развёртывание.

Cutover: сохранить snapshot, остановить старые cron/services/Freqtrade/JS trading loops, сверить и явно согласовать позиции/ордера, проверить один owner account lock. Default старт flat; takeover не делать молча. Live activation требует конкретных venue/account, config/profile hashes, плеч, caps, execution policy и reserve/restart policy. Backtest/optimizer не могут сами активировать live. Rollback начинается со сверки фактических позиций, а не с автоматического запуска прежнего бота.
