# CoinMaster — целевая архитектура и завершение торгового MVP

**Версия 1.0 · 26.09.2026 · задание управляющему чату Codex**

## 0. Назначение и исходная точка

Цель итерации: работающий BTC/SOL-продукт с понятным GUI, проверенным полным циклом исполнения и переходом от уже запущенного Sandbox к отдельно разрешённому минимальному Hyperliquid live-депозиту. Исследования и оптимизация продолжаются независимо. Цель экономики стратегии неизменна: **максимальный конечный ACTIVE + RESERVE после расходов**, без автоматического штрафа за DD, Sharpe или количество ликвидаций. Корректность исполнения не подменяет проверку доходности, и наоборот.

Документ консолидирует предыдущий аудит `CoinMaster_MVP_First_Trade_Codex.md` и требования к архитектуре/процессу. Он заменяет прежний порядок системных доработок; не отменяет утверждённые правила стратегии, разрешения на развёртывание и ограничения доступа. Старые документы и расчётные архивы исполнителям читать не требуется.

**База аудита:** `VF78/coinmaster`, ветка `codex/nautilus-btc-sol-mvp`, commit `3bea52c421df3e0a0f3363c3c8b97110f88a6922`; при подготовке документа remote HEAD совпал. По журналу репозитория установлен Sandbox-release `626fd337639e8b8b4d3a45c00614728d465220d0`. Это не независимая проверка VPS. Аудит исходников и изолированных условий не заменяет интеграционные тесты проекта; финансовый эффект дефектов не измерен.

Перед работой сверить фактический локальный HEAD, незакоммиченные изменения, установленный release, конфигурацию и уже закрытые issues. Задача, уже корректно выполненная на актуальном коде, получает ссылку на доказательство, а не повторную реализацию.

## 1. Целевая архитектура

```text
Браузер: существующий React GUI
          │ HTTPS / session / CSRF
          ▼
Существующий FastAPI / control plane
  ├── конфигурации, исследовательские задания, результаты
  ├── read-only проекции состояния trader instances
  └── адресные команды pause / resume / cancel / flatten
          │ локальный аутентифицированный канал
          ▼
Trader instance: один OS-процесс, один native runtime node
  ├── утверждённый код + immutable candidate + execution policy
  ├── domain: решение и состояние эпизода
  ├── strategy adapter: native orders / fills / callbacks
  ├── data adapters: источник сигналов и execution venue явно разделены
  ├── execution adapter: Sandbox ИЛИ внешний HL; один владелец счёта
  └── собственные журнал, checkpoint, cache и логи

Параллельно, независимо:
ResearchJobManager → отдельный research-процесс → native BacktestEngine
  └── свой run_id, data manifest, account, funding journal, artifacts
```

Это **одно семейство торговой логики на Nautilus, не один общий объект движка**. У live/sandbox и исторического прогона разные часы, аккаунты и жизненные циклы. При выборе другой версии Nautilus меняется её интеграционный слой, а не договорённости между GUI/API/domain.

### 1.1. Ответственность компонентов

| Компонент | Владеет | Не должен делать |
|---|---|---|
| Domain | Правила, права на SOL, TP-targets, состояние эпизода | API-запросы, фиктивные fills, отдельный PnL-симулятор |
| Strategy/native node | Отправка и жизненный цикл ордеров, native account/cache | Оптимизация, тяжёлое чтение всей истории в callback |
| Venue boundary | Метаданные, precision, комиссии, маржа, нормализация native facts | Перенос Bybit tiers на HL или маскировка ошибки как пустого счёта |
| Journal/recovery | Намерения, применённые fill IDs, версия состояния, курсоры | Изобретать отсутствующие биржевые события или автоматически повторять неизвестный submit |
| API/GUI | Представление, кандидаты, адресные команды | Создавать exchange-клиент, изменять runtime DB напрямую, автоматически применять победителя |
| Research | Native-прогоны и результаты на указанной модели | Получать приватные торговые ключи, менять работающий release |

Денежный источник — native account/exchange reports. Backend может строить явно обозначенные метрики из этих фактов; frontend форматирует их, но не ведёт собственную торговую бухгалтерию. Domain-количества сверяются с native-позициями, а не считаются отдельной истиной об исполнении.

### 1.2. Процессы и версии

Один торговый instance = одна среда исполнения, один account/subaccount, одна активная версия стратегии, один процесс. BTC и SOL данного портфеля торгуются на одной площадке. Второй venue/вариант — второй instance; общий межбиржевой залог не предполагается. Не разделять одну связанную BTC/SOL-стратегию на два независимых backtest по монетам.

Минимальные идентификаторы, адаптируемые к имеющимся схемам:

```text
instance_id, mode(sandbox/testnet/live), signal_venue, execution_venue,
account_ref, collateral_currency, release_id, strategy_version,
candidate_hash, execution_policy_hash, state_namespace
```

`account_ref` — ссылка на заранее настроенный счёт, не секрет. Native trader/strategy/client-order ID должны различать instances и сохранять прослеживаемость после рестарта.

Активный release не обновляется `git pull` в работающем каталоге. Research использует отдельный checkout/артефакт и зависимости. Публикация GUI не перезапускает trader. Новая конфигурация — immutable кандидат, применение отдельно, обычно после flat. Flat не всегда означает завершённый эпизод: при живых SOL-правах или queued-intents сначала применить установленный lifecycle.

### 1.3. Хранилища и параллельность

Сохранить SQLite для существующих журналов/контроля, Parquet/файлы для исследований и **уже используемый локальный Redis только для native cache**, если он нужен выбранному recovery. Не удалять работающую persistence ради формального «без Redis», но не добавлять новый брокер/кластер.

- У каждого trader и каждого from-genesis run отдельные mutable state и funding ledger. Общий исторический каталог — read-only; новые файлы публикуются атомарно.
- Нельзя делить живые engine/cache/SQLite connections между процессами. Native state изменяется в его event loop; команды из HTTP-thread передаются туда, а не вызывают `submit_order` из веб-потока.
- API читает ограниченную worker-owned проекцию. GET не принимает торговых решений, не refresh-ит всю историю и не должен быть необходим для жизнеспособности трейдера.
- На общей машине по умолчанию один тяжёлый research job. Задать простой лимит RAM/CPU доступными средствами systemd/существующего launcher, проверить запас памяти и диск. Отказ/отмена research не затрагивает trader. Не строить собственный планировщик ресурсов.
- Ключи и runtime-state недоступны research-процессу на уровне service environment/прав файлов. Не достаточно «не обращаться к ключу по договорённости».

### 1.4. Минимальное расширение для будущего SaaS

Сейчас: стабильные идентификаторы, один владелец счёта, изоляция секретов и версий, узкий API. После проверенной эксплуатации: отдельный проект multi-tenant authorization, quotas, billing, onboarding и правовая/product-проверка. Не вводить сегодня пустые tenant-абстракции, generic plugins или микросервисы под гипотетические тысячи пользователей.

## 2. Общие контракты — согласовать один раз

Это целевые семантики, не требование переименовать все существующие классы. Использовать текущие схемы и генерацию TypeScript, где они уже есть.

### 2.1. Runtime projection

Версия схемы; identity/mode; `observed_at`; последнее время native-события; фактическая свежесть данных; последний закрытый день; последнее решение; код блокировки; известные positions/orders; account; режим восстановления; доступные команды и причина недоступности.

Различать:

- `RUNNING/WAITING_SIGNAL` и `DATA_STALE`;
- нормальные owned resting TP и `RECOVERY_REQUIRED`;
- достоверный пустой счёт и `UNKNOWN/INCOMPLETE/ERROR`;
- последнее известное значение со stale timestamp и актуальное значение;
- native cash, marked equity, free collateral и зарезервированную маржу.

`ACTIVE_OWNED_REDUCTIONS` в текущем подтверждённом процессе — не восстановление после аварии. После рестарта та же запись сама по себе не даёт разрешения торговать. `recovery_required` должен вычисляться одной согласованной функцией, не сравнением всех состояний с одной строкой `FLAT_RESTART`.

Ордер: account/instance, native ID, instrument, side, type/TIF, price, requested/filled/leaves quantity, reduce-only/post-only, status, timestamps. Поля вводить только когда доступен их native источник; отсутствие — `null` + статус, не фиктивное значение.

Деньги/точные количества передаются decimal-строками. Ставки/доли имеют явные единицы: `0.03` в API = `3%` в GUI. Нуль счёта — возможный экономический факт, а не отсутствие данных. Отрицательный/аномальный баланс нельзя молча заменять нулём.

### 2.2. Команды

Команда привязана к `instance_id`, действующему режиму и `idempotency_key`. Повтор с тем же ключом и payload не исполняется дважды; другой payload с тем же ключом — конфликт.

`accepted` не означает `executed`. Для pause/resume возвращать прочитанное состояние; для cancel/flatten — progress/result по фактическим acknowledgements/fills. Не объявлять flat до нулевых позиций и отсутствия заявок, способных снова создать экспозицию. Поздний fill после cancel обрабатывается и пересчитывает остаток.

## 3. Рабочие пакеты

Все проблемы ниже взяты из предыдущего аудита либо обозначены как проверка контракта. Управляющий сначала подтверждает актуальность, затем ставит root-cause fix. Не закладывать финансовый эффект исправления без нового прогона.

### CM-00 — единая исходная точка и минимальный release-процесс

**Приоритет:** сейчас. **Зависимости:** нет.

Сверить локальный/remote commit, установленный процесс, candidate/policy/release, домен и режим. По каждому нижеследующему пакету: `OPEN / ALREADY_FIXED / PARTIAL / NEEDS_REPRODUCTION`, короткое доказательство. Оставить один актуальный верхний блок статуса в существующем checkpoint; старую хронологию не перечитывать каждому исполнителю.

Классифицировать ранее отмеченные 29 test failures: относятся ли они к действующему money/order/API пути, недостающим локальным fixtures либо архивному коду. «Ошибка была раньше» не означает допуск. Не исправлять весь legacy ради зелёной общей цифры; release-suite действующего пути должен проходить.

Release manifest собирается автоматически: commit/dirty-status, полный набор исполняемого кода, candidate, execution policy, pinned dependencies. Один hash `strategy/wave_overlay.py` не удостоверяет неизменность domain/venue. Сохранить rollback и существующие approval-границы, убрать ручное дублирование метаданных. Не превращать каждый комментарий в отдельное согласование.

**Готово:** известна фактическая исходная точка, тестовый baseline и область изменения; будущие commits проверяются относительно неё. GitHub Project синхронизирован по разделу 7.

### CM-01 — единый непустой контракт worker → API → GUI

**Приоритет:** блокер проверки первого ордера. **Зависимости:** CM-00.

Файлы: `ops/hyperliquid_testnet.py`, `ops/hyperliquid_testnet_worker.py`, `ops/paper.py`, `api/runtime_sidecar.py`, `web/lib/nautilusApi*`, `web/pages/NautilusControlPage.tsx`.

В аудите: worker выдаёт `reduce_only`, а strict `HlStagegOrder` его запрещает; известные TP дают ложный recovery-флаг и могут убрать текущий cash из проекции. Исправить producer/consumer и классификацию по §2, не отключать strict validation глобально. Генерируемые клиентские типы и отображение должны соответствовать одному контракту.

Добавить read model «почему сейчас нет сделки»: последняя парная сессия, side, валидность beta/waves, последняя попытка/результат, pending parent, блокировка и следующий момент оценки. `PUBLIC_FEEDS_READY` не означает, что стратегическое решение выполнено.

**Готово:** реальный payload от native-worker проходит API и GUI для flat, позиции с тремя TP, partial, cancel, stale и unavailable. API-offline не отображается как flat/нулевые деньги. Это контрактный тест, не вручную подогнанный mock.

### CM-02 — zero-fill и полный дневной lifecycle

**Приоритет:** блокер торговли. **Зависимости:** CM-00; поля диагностики согласовать с CM-01.

Файлы: `domain/wave_overlay.py`, `strategy/wave_overlay.py`, `ops/hyperliquid_testnet.py`, `ops/stage_g_refresh.py`, существующий checkpoint.

**Zero-fill:** episode сейчас создаётся до исполнения BTC_ENTRY; после доказанного нулевого terminal остаётся без VWAP/H и последующие решения могут всегда возвращать пусто. Завершать только действительно неоткрытый эпизод при отсутствии другого pending-risk. Любой partial сохраняет эпизод. Неизвестный ACK/transport timeout требует reconciliation, а не нового ордера.

**Повторы:** ограниченная политика для transient-denial и следующего разрешённого сигнала; реальный отказ, доказанная отмена и неизвестный исход различаются. Не бесконечный submit на каждой котировке. Разделить identity дневного решения и identity конкретной разрешённой попытки исполнения.

**UTC:** сохранять последнюю непрерывную закрытую сессию, принятое/отложенное решение и причину. Живой бар и backfill проходят один идемпотентный путь. Duplicate/out-of-order не удваивают историю или вход; поздний SOL-bar корректно дополняет BTC-bar. Не требовать новой полной warmup-выгрузки, если уже есть проверенная непрерывная live-история.

Пропуски догружать из того же signal-source: обновить признаки по закрытым дням, не разыгрывать упущенные сделки по старым ценам. Политика актуальности deferred-сигнала явная; исполняется лишь разрешённое текущее решение на следующем доступном событии. Не приписывать этому policy-change прежний ROI.

В текущих правилах flat + валидные beta/waves + разрешённый день ведут к BTC_ENTRY; SOL-z не является условием первоначального BTC-входа. Если входа нет, журнал показывает конкретную причину.

**Готово:** тесты local denial, rejection, IOC zero-fill, partial+cancel, unknown ACK, новая сторона; replay UTC, поздний бар, duplicate, gap/backfill, pause/resume, рестарт во время ожидания. Нет вечного flat-зависания, дублирования или будущих данных.

### CM-03 — единый исполнительный и денежный контракт

**Приоритет:** до малого live; дефекты первого цикла — немедленно. **Зависимости:** CM-02; тот же владелец strategy-файлов.

1. Использовать последнюю причинную пару BTC/SOL marks с явными max_age/max_skew. Точное наносекундное равенство — не условие живой проверки. Не применять stale/будущую цену. Проверять свежую equity при новом ордере, не сохранённые marks вчерашнего решения.
2. Определить по фактическому адаптеру: `balance_total` — cash или уже equity; не прибавлять unrealized дважды. IM, MM, pending reservation, fees и free collateral различны. Проверить текущий gate на повторное резервирование IM; это адресная проверка, а не утверждение измеренного влияния на ROI.
3. Side-aware executable price; округление по инструменту; min/max quantity/notional; ожидающие increases входят в бюджет. Reduce-only не превращается округлением в новый риск. Остаток меньше шага отмечается явно, не «скрытый flat».
4. Повторно проверить уже внесённые исправления: pending SOL не мешает обязательному выходу; timeout не создаёт add→немедленный exit; pause проверяется перед каждым увеличением; partial BTC TP выдаёт только подтверждённое SOL-право; замена TP считает leaves от исходной цели, не от последнего ордера.
5. Не менять принятую SOL-exit policy задним числом. После предыдущего аудита z-выходы переведены в явный taker-control; уточнить действующий policy. Maker — только реальная native liquidity-side, не label market-ордера. Гипотеза «отключить z-выходы ради ROI» остаётся отдельным research-кандидатом.
6. Разделить локальное принудительное закрытие, exchange liquidation и неизвестное внешнее изменение. Не синтезировать доказательство биржевой ликвидации из собственного предположения.
7. Funding rate/next-payment — не уже состоявшаяся выплата. Live account обновляет реальный адаптер; журнал не начисляет ту же выплату второй раз. Для Sandbox допустимо честное `UNPOSTED` до отдельной реализации; его PnL не называется net-after-funding.

Комиссии исследовательских baseline: Bybit maker `0.00020`, taker `0.00055`; HL maker `0.00015`, taker `0.00045` — согласованные допущения проекта, не гарантия тарифа любого аккаунта. Fixture `0.001` не возвращать. Volume discounts пока вне критического пути; в live регистрировать фактическую комиссию.

**Готово:** native regression для частичных/отменённых заявок и fresh/stale/asynchronous marks; проверочный account-пример без двойного PnL/маржи; обязательный exit не блокируется alpha/warmup-gate. При отсутствии возможности исполнить выход — явная ошибка/повтор/уведомление, а не выдуманный flat. Новые стопы/снижение плеча/ограничение риска без отдельного изменения стратегии не добавлять.

### CM-04 — доказать первый полный виртуальный цикл

**Приоритет:** сразу после критических исправлений. **Зависимости:** CM-01, CM-02, относящаяся к циклу часть CM-03.

В отдельном процессе/namespace проиграть запись проблемного UTC-перехода и короткий детерминированный сценарий: сигнал → entry → partial/terminal → TP → SOL add → half/full/mandatory exit → flat → новый эпизод. Стратегия и native callbacks те же; ускоряется тестовый clock, не время VPS. Никаких принудительных тестовых заявок в естественном Sandbox-журнале.

Проследить одно ближайшее естественное решение. Не ждать неделями всех редких рыночных событий: их покрывает replay. Если естественного входа нет, есть проверяемое объяснение, а не только `READY`.

**Готово:** артефакт цепочки signal→intent→order→fill, проверка cash/qty, непустой GUI contract и отсутствие зависания следующего эпизода. Результат функционального теста отдельно от доходности стратегии.

### CM-05 — закончить native HL adapter/recovery, один путь версии

**Приоритет:** блокер необслуживаемого live; продолжение #110. **Зависимости:** CM-00; интеграция после CM-02/03. Изолированную проверку адаптера можно начать раньше без изменения общих файлов.

Файлы: `ops/live_recovery.py`, `strategy/live_recovery.py`, существующие persistence/tests и HL native adapter выбранной версии.

В исходном аудите pinned HL 1.231 bulk reports возвращают `[]` при исключениях. Проверить и устранить различие: достоверно пусто / неполно / transport failure / parse failure. Неполный history-window или cap не доказывает flat. Не достаточно HTTP 200 или теста только пустого аккаунта.

Завершить имеющиеся durable intents, versioned episode, native cache и cursor применённых fill IDs. Применение fill и обновление checkpoint атомарны относительно journal; повторный report не удваивает объём/комиссию. История не должна требовать невозможного полного архива с первого дня: проверяется достаточное непрерывное окно от собственного checkpoint с явной полнотой.

**Решение по версии:** сохранить работающий Sandbox; сравнить один ограниченный вариант исправления текущего адаптера с уже начатой квалификацией rc5/актуальной допустимой версии. Выбрать путь по рабочему вертикальному срезу orders/fills/recovery и ожидаемым переделкам, а не номеру релиза. Не вести одновременно собственный большой Rust-fork и полную миграцию. Версию и native API зафиксировать; partial migration с несовместимыми model types запрещена. Изменение движка — отдельный release; GUI/domain не переписывать из-за импортов.

**Готово:** submit→потерянный ACK; partial→crash→restart; native reconciliation принадлежащих позиций/заявок; следующий TP/SOL/выход без дубля; malformed/truncated/error не допускают takeover. Необъяснимое ручное изменение остаётся `RECOVERY_REQUIRED`. Полная автономная обработка всех ручных вмешательств не является условием микро-MVP.

### CM-06 — GUI для трейдера, а не панель технических допусков

**Приоритет:** делать параллельно после фиксации CM-01. Операционный минимум — до live; расширение исследовательских форм — после.

Сохранить React, существующие страницы и авторизацию. Не переносить backend в другой стек, не оживлять Freqtrade/JS-PnL. Передавать GUI-исполнителю только API-контракт и его файлы.

**Dashboard / Runtime:** точный режим и instance; последняя дневная оценка/причина отсутствия входа/следующее действие; native cash и marked equity; realized/unrealized, fees/funding со статусами; BTC/SOL side/VWAP/qty/notional/mark/TP; заявки с заполнением и остатком; лента решений и fills. Хеши под details, не вместо содержательных значений. Read-only projection доступна и при pause/recovery.

**Управление:** pause/resume и cancel/flatten этого instance; подтверждение реального режима/счёта, pending command и прочитанный результат. Кнопка недоступна только с конкретной причиной. Не переиспользовать terminal-backtest settlement как скрытый live flatten; операторский выход имеет отдельный reason и не запускает автоматический повторный вход.

**Strategy:** работающая версия read-only; «создать исследовательскую копию» из неё, не из старого v0; diff настроек; полная immutable-конфигурация, включая флаги late SOL/beta. Ввод процентов единообразен для numeric/decimal-string; arrays валидируются до сохранения. BTC×ACTIVE, SOL×H и exchange leverage подписаны раздельно. Apply/promote — только проверенный отдельный путь, не следствие Save.

**Research:** start/status/cancel/result действующего native job, текущий честно обозначенный scope поиска. Вывод equity-кривой/месяцев/сделок из существующих артефактов, когда доступно. Не обещать график, если backend его не экспортировал. После первого micro-live — пользовательские периоды/несколько осей и лимит числа прогонов, без новой оптимизационной платформы.

**Приёмка:** авторизованный desktop и mobile; flat/populated/partial/recovery/stale; длинные суммы; 401/ошибка API; повтор команды; research cancel. Реальный непустой backend-контракт + отдельный визуальный fixture допустимы, но mock не называется live-проверкой. Данные аккаунта приватны, секреты отсутствуют в браузере и логах.

**Готово для micro-live:** оператор видит почему бот действует/не действует, фактическую экспозицию и рабочие заявки, получает нужное состояние и может остановить увеличения/закрыть позиции. Полировка всех графиков и гибкий optimizer не задерживают этот рубеж.

### CM-07 — эксплуатация и изоляция, без нового инфраструктурного проекта

**Приоритет:** существующее сохранить; недостающий минимум — до live. **Зависимости:** CM-00, контракты CM-01.

Один VPS допустим. Существующие systemd/reverse proxy/TLS/session auth не заменять. Использовать namespaces и отдельные service environment для Sandbox/live/research. Official native execution adapter, ключ только у нужного trader, реальный account address отдельно от signing-agent. Не вставлять master/private key в issue, JSON кандидата или prompt.

Зафиксировать выбор владельца счёта: локальная блокировка/существующая lease не допускает второй исполнитель того же account на этом deployment. Не считать её распределённой гарантией на произвольных чужих хостах. Research/API не имеют shell-доступа к произвольным командным строкам через веб-форму; только существующий allowlist.

Replay/research cancel завершает только принадлежащую ему группу процессов. Ограничить concurrent jobs и память перед совместным запуском; smoke доказывает, что trader принимает события и команды при research-load. GET-status не держит тяжёлую работу на native loop. DB snapshots согласованы с sequence/revision; не читать изменяемый cache из HTTP-потока как якобы атомарный факт.

Release: один воспроизводимый build + manifest, адресное обновление одного сервиса, проверка установленного кода, rollback. При открытой позиции запрещён слепой rollback к несовместимому checkpoint; сначала подтверждённое управление/flat. GUI-deploy не перезапускает торговлю. Использовать существующий канал уведомлений о фатальном сбое/неизвестном submit/stale с экспозицией; не разворачивать observability-платформу.

**Готово:** подтверждённая независимость trader/research/API, действующая авторизация, корректный адресат команд, controlled restart и rollback, понятный health. Ненужные старые сервисы убирать только после сверки использования; не менять соседние работающие проекты.

### CM-08 — малый реальный тест и запуск неизменяемой стратегии

**Приоритет:** конечная цель итерации. **Зависимости:** CM-04, CM-05, CM-07, CM-03 и операционный минимум CM-06.

Настоящее внешнее testnet-исполнение, если оно доступно без отдельного большого проекта, полезно для проверки подписания/ACK/cancel; оно не заменяет mainnet-ликвидность. Не переименовывать локальный Sandbox в такой тест.

Подготовить отдельный live instance и заранее согласованный технический сценарий: ограниченный номинал, place/cancel, исполнение, reduce/flat и read-back. **Сумма депозита, счёт и внешние ордера требуют отдельного явного разрешения владельца.** Ключ не запрашивается в чате. Технический капитал выбирается после проверки minimums и частей сделки; не считать любую сумму автоматически достаточной.

Сначала технический smoke отдельно помечается и не входит в статистику естественной стратегии. Затем запускается зафиксированная версия на разрешённом капитале; реальные fees/funding/исполнения сверяются. Нет автоматического пополнения, увеличения капитала или переключения кандидата.

**Готово:** биржевые/native order IDs, cash/qty/funding сверка, cancel/partial/restart/выход работают; нет неизвестной экспозиции. «Технически работает» не маркируется «доходность доказана».

### CM-09 — параллельное исследование и следующий продуктовый рубеж

**Приоритет:** вне критического пути первого live. **Зависимости:** рабочая модель CM-03/04, изоляция CM-07.

После изменения order semantics отдельно пересчитать точный замороженный кандидат и сопоставить различия с прежним Stage G; не ждать этого полного двухлетнего отчёта ради локального технического smoke. Новый ROI публикуется только после реального соответствующего прогона.

Последовательность исследований: точный BTC-only; strict/late SOL при той же финальной конфигурации; явные SOL-exit policies; небольшая совместная окрестность размеров. Расширять поиск только при экономическом результате, не ради числа попыток. Уже выполненные проверки не повторять без изменения кода/данных/политики. Резерв/рестарт не эмулировать несуществующим переключателем.

Новые результаты — отдельные candidate/release/data/policy hashes, отдельный funding journal. Лучший TOTAL не меняет live автоматически. Две биржи/две версии реализуются тем же instance-шаблоном позднее; их капиталы и статистика раздельны. Будущий SaaS — backlog, не условие проверки собственного счёта.
