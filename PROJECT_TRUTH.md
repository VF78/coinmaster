## Ключевое правило исполнения
- Любые **кодовые изменения** выполняются через **Claude Code CLI** (модель **opus 4.6**) в репозитории.
- Только короткие итерации с регулярным статусом.
- Никаких длинных монолитных сессий без отчёта прогресса.
- Надёжность важнее скорости.

## Приоритеты Coinmaster
1. uptime / стабильность
2. observability (логи, health checks, статусы)
3. воспроизводимые команды запуска/проверки
4. безопасные изменения (малые диффы, контроль регрессий)
5. только после этого — новые фичи

## Обязательная операционная модель
1. Принимать задачу и классифицировать:
   - infra/devops
   - bugfix
   - feature
   - refactor
   - diagnostics
2. Разбивать работу на кванты по 20–45 минут.
3. Готовить точные Task Packet для Claude Code.
4. После каждого кванта давать отчёт в фиксированном формате.
5. Не допускать попадания длинных логов/дампов в основной контекст.
6. При проблемах канала/процесса давать диагностику и безопасный restart plan.

## Формат каждого ответа по рабочей задаче
- Статус
- Цель текущей итерации
- План (1–2 подзадачи)
- Команды проверки (точные)
- После выполнения: что сделано / что проверено / что дальше

## Шаблон постановки задачи для Claude Code (обязательный, использовать всегда)

```md
Задача (квант 20–45 мин): [короткая цель]

Контекст:
- Репозиторий: [path]
- Связанный проект/карточка: [GitHub Project item / issue]
- Почему это важно: [1-2 предложения]

Сначала (explore/plan, без изменений):
1) Изучи файлы: [список]
2) Найди существующий паттерн для [X]
3) Кратко опиши план изменений (списком)

Потом (implementation):
- Сделай только:
  1) ...
  2) ...
- Не меняй:
  - ...
  - ...

Проверка (обязательно выполнить):
- Команды:
  - [build/test/lint/typecheck]
- Ожидаемый результат:
  - ...

Формат ответа:
- Что сделано
- Какие файлы изменены
- Результат проверок
- Что осталось/риски
```

## Анти-залипание (обязательное)
- Если нет подтверждённого прогресса 10–15 минут → статус `blocked`.
- Если проблема воспроизводится → сначала минимальный reproducible case.
- После 2 неудачных попыток → стоп + гипотезы + что нужно от человека.

## Качество (обязательное)
- Порядок: diagnosis/explore → plan → implementation → verify.
- Перед статусом «готово» обязательно:
  - проверить запуск,
  - проверить ключевой сценарий,
  - зафиксировать риски.
- При изменениях infra/конфига всегда давать rollback-шаг.

## Чувствительные изменения (торговля/бот)
- Не менять торговую логику, risk-параметры и execution path без явного указания Владимира.
- Любые изменения стратегии сопровождаются:
  - гипотезой,
  - способом проверки (backtest/dry-run),
  - перечнем рисков.

## Стартовый режим (текущий этап)
Первый запуск — только структурирование, без крупных кодовых изменений:
1. Быстрый аудит репозитория и структуры запуска.
2. Выделение:
   - точек отказа,
   - мест для health checks,
   - мест для логирования/наблюдаемости,
   - быстрых мер повышения стабильности.
3. Сопоставление с GitHub Project #2.
4. Предложение операционного минимума:
   - команды запуска,
   - команды диагностики,
   - команды проверки,
   - шаблон отчёта по итерациям.
