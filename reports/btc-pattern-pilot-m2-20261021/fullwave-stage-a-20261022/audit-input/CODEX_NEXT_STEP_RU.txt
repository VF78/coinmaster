Числа относятся к сохранённым UTC close-time и консервативному учёту raw hourly bar starts. Проверить именно эту конвенцию. Отдельно документировать рекурсивную историю детектора.
Единое правило для query, всех библиотек, prior и scaler. Не сдвигать origin в экстремум.
Регрессии: E00203 расширение 34h и pool193→192 с исключением E00196; E00307 расширение 2h и pool297 неизменен. Все 198 queryIDs остаются.
Не приписывать гипотезе улучшение, возникающее только из исправления общей библиотеки.

0.2. Для свободных LLM-прогнозов добавить проверки согласованности:
u=D_UP, d=D_DOWN, n=D_NONE;
T_up=short.sl_100.p_adverse_touch;
T_down=long.sl_100.p_adverse_touch.
u<=T_up<=1−n; d<=T_down<=1−n; T_up+T_down>=1−n, tolerance1e-6.
Старые ответы не ремонтировать. Неоднозначность внутриминутных first-passage labels хранить явно; не превращать её в выдуманный однозначный исход.
Эмпирический D с отдельным исключением ambiguous-путей может иметь иной знаменатель: не утверждать общей калибровки/согласованности без проверки общего контракта.
Linux ru_maxrss переводить из KiB, Darwin оставлять bytes; это ресурсный, не прогнозный фикс.

1.1. До новых прогнозов сохранить metadata-only сравнение доступности:
OLD_STRICT: прежнее требование label_end<=earliest_query_feature_support, с исправлением этапа0.
CAUSAL_WALK_FORWARD: новый явно выделенный исследовательский режим. Все используемые исторические исходы должны созреть к заранее фиксированному fold fit_cutoff, который не позже query decision_time. Каждый исторический input построен только из его собственного прошлого. Запрос использует только данные, доступные к его decision_time. Предобработка и параметры fit-only. Query future не участвует ни в одном преобразовании.
Первый режим проверяет сильное разделение всей истории. Второй соответствует доступности информации при реальном прогнозе. Известная прошлая цена может входить и в исторический исход, и в сегодняшнюю EMA; это не разрешение использовать будущее.
Фиксировать fold cutoff; в данном этапе не добавлять rolling refit и адаптивную перекалибровку. Индекс содержит только зрелые события разрешённого fit prefix.
Никакой случайной train/test разбивки. Label horizons обучающих примеров не пересекают начало будущего тестового периода. Никаких будущих закрытий D1, финальных экстремумов и полной будущей длительности волн в query features.
Показать число доступных событий и условных состояний в обоих режимах. Никаких forecast comparisons для выбора выгодного режима задним числом.
Основной новый опыт выполнять по CAUSAL_WALK_FORWARD как отдельный протокол, одинаковый для всех новых baselines и Astra. Старые строгие результаты не переписывать и не выдавать изменение библиотеки за пользу модели.
Перекрытие прошлого не делает примеры независимыми: сохранять72h разделение соседей, хронологическую оценку, календарные и эпизодные отчёты. Для утверждений о100–200дневных циклах нужен отдельный счёт циклов и более длинная проверка;14/28d интервалы этого не доказывают.
Если любой invariant причинной доступности нарушен, сначала исправить его и остановить прогнозную часть до исправления. Не ослаблять проверки будущих данных ради заполнения библиотеки.

1.2. На одной библиотеке нового режима рассчитать:
A. Global event prior.
B. Phase E1 k32/prior-mass8 с тем же новым контрактом. Называть это пересчитанным контролем, а не историческим E1.
C. DAILY90: знак log(last_closed_D1_close / D1_close_90days_earlier), два состояния.90 дней — фиксированная исследовательская гипотеза, не оптимальный найденный период и не полный цикл.
F_mix=(n_state*F_state +32*F_global)/(n_state+32).
Один prior-mass32, без поиска порога/периода. Не делать четыре группы и не перемножать daily state с ними. EMA34/180d не запускать как дополнительные кандидаты.
Неизвестное/пустое состояние или точный ноль →global prior. Раннюю историю с недостаточным D1 warmup оставить в общем prior; не выдумывать state.
Общие неотрицательные веса исторических исходов для18 MFE квантилей и6 adverse-touch вероятностей. Квантили — обратная взвешеннаяCDF, не среднее квантилей.
Показать фактические n_state, prior weight, reuse и fallback; число событий не равно числу независимых циклов.
DAILY90 оценить на всех198 исходных общих query и отдельно на24 query следующего этапа. Результаты разных популяций не смешивать.
Это нулевое обучение нейросетей и0 LLM-вызовов.

ЭТАП 2. НОВАЯ РОЛЬ ASTRA: РАНЖИРОВАНИЕ ФОРМЫ БЕЗ ИСХОДОВ
Модель: явно gpt-6-astra; reasoning=max. Это пользовательский выбор для предиктора и он имеет приоритет над экономным executor-default.
Записать реально выбранные настройки. Если эта модель недоступна, отметить этап INCOMPLETE; не подменять молча Sol. API с отдельной оплатой не подключать вместо разрешённого in-app способа.
Не считать название модели гарантией качества; не делать утверждения об обучении её весов.

2.1. Отобрать 24 query из исходных 198 зрелых E1 событий:8 календарно равномерных слотов на fold; ближайшее допустимое событие к центру слота, при равенстве раньше.
Сохранить label_end внутри fold и неперекрытие выбранных 72h будущих интервалов. Если невозможно заполнить, явно UNDERFILLED, без выбора по исходу.
Список, конфигурацию, хеши и все входные пакеты зафиксировать до запуска Astra.
Эта история уже исследовалась; называть результат exploratory DEVELOPMENT, не pristine holdout.

2.2. На каждый query взять 8 кандидатов из причинно допустимой прошлой библиотеки CAUSAL_WALK_FORWARD:
- исходная phase/state distance E1;
- прежний стабильный порядок при равенстве;
- greedy72h separation;
- никаких будущих данных текущего query;
- n<8 → общий prior и явный insufficient_support, query не удалять.
k8 фиксирован для ограниченного размера пакета и более локального сравнения; это не найденный по PnL оптимум и не сетка.
Все сравниваемые ранжировщики получают ОДНИ И ТЕ ЖЕ 8 кандидатов.

2.3. Вход Astra:
- наблюдённые query и 8 исторических prefix;
- одинаковые поля контекста и единицы;
- 64×1h и 64×4h OHLCV, только закрытые бары, при наличии причинного полного event-prefix — его phase32+32 и реальные длительности частей;
- цена каждого эпизода как log(price/own last-known close)/own sigma72, scale только по уже известному прошлому;
- одинаковые правила рисунка и читаемые оси, нормализованные числа — первичный источник;
- никакого календарного названия, абсолютной цены, entry из будущей минуты, текущих новостей или будущих исходов query;
- также НИКАКИХ исходов 8 кандидатов в пакете ранжировщика. Они будут использованы только отдельным численным модулем после запечатывания ранжирования.
Лимит JSON250KB; не обрезать молча последние/важные бары ради лимита.

2.4. Задача модели:
упорядочить 8 candidate IDs по сходству наблюдаемой структуры с query; указать no_match и короткое структурное объяснение с конкретными координатами/участками.
Выход только JSON:
{query_id, ranked_candidate_ids, no_match, evidence}.
Ровно 8 уникальных разрешённых IDs в ranked_candidate_ids, даже при no_match; никаких прогнозных TP/SL, свободных вероятностей, новых IDs и вызовов других моделей.
Фиксированный prompt и schema, свежий fork_turns=none на каждый query. Не передавать текущий исследовательский чат, repo/results, память или исходы; запретить browse/другие файлы.
Один ответ; не ретраить по качеству. Невалидный/отсутствующий ответ →fallback prior, учёт в denominator.
Допустить 2 fit-only форматных debug ответа, затем freeze. Общий hard cap26 ответов, без повторного выбора модели/prompt по evaluation.

ЭТАП 3. ОДНО ЧИСЛЕННОЕ ПРЕОБРАЗОВАНИЕ РАНГА В ПРОГНОЗ
Сравнение на одинаковых 24 query:
- global prior;
- DAILY90 prior;
- phase k32 по тому же новому контракту;
- NUMERIC8:8 кандидатов в исходном численном порядке;
- ASTRA8: те же 8 в запечатанном порядке Astra.

NUMERIC8 и ASTRA8 имеют одинаковую формулу весов:
H8=sum(1/r,r=1..8);
local_weight(r)=8/(H8*r);
global prior total mass=8, равномерно по всей той же eligible past pool.
Итого local-mass8 + prior-mass8. Повторное вхождение локального ID в global component — корректная смесь, не ошибка; итоговый вес события складывается.
Исключение: ASTRA no_match/invalid/insufficient →global prior; сохранять в общей оценке и отдельно показывать покрытие.
Параметры не подбирать после получения исходов.
Разница ASTRA8−NUMERIC8 теперь относится к ранжированию/отказу Astra, а не к разным библиотекам, k или сглаживанию.

Дальнейшие исходы кандидатов доступны численному модулю только как зрелая прошлая история. Одни и те же веса применяются ко всем side/SL:
- Q20/Q50/Q80 MFE-before-SL;
- full72h adverse touch.
При необходимости D вычислять с явно указанной обработкой ambiguous-исходов.
Всё брать из существующих target definitions; не менять физический SL, горизонт или вход ради улучшения.

ЭТАП 4. ОЦЕНКА И ОСТАНОВКА
Сначала запечатать все ответы, затем присоединить query truth и выполнить scoring один раз.
Основные метрики прежние: mean18 pinball в sigma72 и mean6 Brier. Сравнения парные по query.
Публиковать все 24 ID, все folds, all-ID/fallback, n_eff=(sum w)^2/sum(w^2), reuse, размер прошлой библиотеки, частоты и квантили по всем side/SL.
Дополнительно показать, улучшает ли порядок Astra сходство будущих исходов относительно NUMERIC8 на тех же query/candidates. Эта диагностика выполняется после запечатывания ответов; она не должна использоваться для отбора удачных аналогов задним числом.
Не считать 18/6 выходов независимыми наблюдениями. Уровни TP разных моделей нельзя ранжировать только по hit rate.
Повторить прежний paired14d bootstrap и 28d sensitivity как описательные интервалы; явно указать малый размер выборки.
Формальный DAILY90 gate: обе co-primary ошибки лучше global prior, upper95%14d<0, минимум 2/3 folds с улучшением; против пересчитанного phase в том же новом контракте нет ухудшения обеих pooled метрик. Зафиксировать одну трактовку gate для всего отчёта.
Для 24-оконного Astra screen не заявлять пригодность к торговле даже при положительном результате. Если обе основные ошибки не улучшены против NUMERIC8, автоматического расширения Astra нет. Если улучшены, показать величину эффекта, неопределённость и стоимость расширения при фиксированной конфигурации; текущий cap26 не превышать. Не менять рецепт для спасения результата.
