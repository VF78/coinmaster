АУДИТ BTC PATTERN PILOT — 22.10.2026

Проверенный последний содержательный отчёт:

Предыдущие эксперименты закреплены в 0a9a63569c887f5e4f1de81c2b88001a2ebe3d59. Новый postmortem не меняет их прогнозы.

ВЫВОД
Реальные дефекты существуют, но они не объясняют отрицательный результат. Главное установленное поведение: найденное сходство прошлых форм не даёт достаточно устойчивой связи с будущими исходами; локальным поправкам отдан слишком большой вес относительно их полезности. Это описание ошибок проверенной системы, не доказательство отсутствия любых рыночных паттернов.

В E1 не обучали нейросеть и не вызывали ChatGPT. Там фиксированный причинный детектор подтверждённых разворотов, фиксированные признаки и эмпирические прогнозы по аналогам.
В отдельном опыте ChatGPT использовали GPT-6.1 Sol/high, четыре исторических примера и 24 оценочных окна. Примеры выбирались по 12 контекстным полям, без сходства свечной последовательности при отборе. P получал подробные окна и график после этого отбора. Это не полный поиск графических паттернов.

Простое постоянное смешивание E1 с prior не сильное исправление. Даже hindsight-оптимальный общий коэффициент вдоль этой же сохранённой поправки даёт максимум 0.0676% относительного улучшения Brier в данной выборке. Это не ограничение всех будущих моделей.

2. РЕАЛЬНЫЕ ДЕФЕКТЫ
A. Прямая зависимость порога волны не полностью включена в input_start.
Консервативная граница:
min(existing_input_start, activation−169h, anchor−1h).
E00203: расширение 34 ч, pool193→192, исключается только E00196.
E00307: расширение 2 ч, pool297 не меняется.
E00196 не выбран ни одним из state/clock/phase; затрагивает prior и scaler.
Это нарушение строгого исключения перекрытия историй, а не использование будущих цен относительно текущего момента.
Диагностическое исключение 2 точек почти не меняет отрицательный итог; не удалять их из официального результата.
Рекурсивную историю детектора нужно описать отдельно от конечного числового окна признака.

B. Проверка JSON прогнозов не связывает D с вероятностями касания SL1.
u=P(UP-first), d=P(DOWN-first), n=P(NONE);
T_up=short.sl_100.p_adverse_touch;
T_down=long.sl_100.p_adverse_touch.
Необходимы:
u <= T_up <= 1−n;
d <= T_down <= 1−n;
T_up+T_down >= 1−n.
В старых 24 C ответах два нарушения; в 24 P —0.
Это дефект валидации, но не объяснение провала P против prior.
Сохранённые ответы не переписывать задним числом.

C. Второстепенная переносимость: ru_maxrss на Darwin в байтах, на Linux в KiB. Guard E1 предполагает Darwin. Это не причина качества прогнозов.

3. ЧТО УЖЕ ПРОВЕРЕНО
FORM уже исправил 80h engineered-support, добавил контекстную модель, Flat780 и CNNSpatial2x8. Все итоговые допуски отрицательны. Не повторять эти опыты как новые идеи.
Исходная CNN улучшает short-Q относительно контекста, но практически не улучшает его относительно prior. Отрицательный gate не доказывает нулевую информацию в изображениях.

4. НОВЫЙ НЕБОЛЬШОЙ ОПЫТ ASTRA В ЭТОМ АУДИТЕ
Явно выбран gpt-6-astra/max. Шесть прежних окон: нулевые календарные слоты 2 и 5 каждого fold; правило и входные хеши закреплены до новых ответов. Две ветки на окно:
P — прежний подробный пакет + график;
C — прежний контекстный пакет.
12 свежих контекстов, по одному ответу,0 повторов. Предикторам не передавались результаты/исходы текущего окна. Все 12 ответов запечатаны до scoring. Это процедурная изоляция, не доказательство отсутствия данных в pretraining.
Исходный prompt по смыслу неизменен (локальная копия содержит дополнительный завершающий перевод строки). Исторические пакеты извлечены из архива с SHA25639dc8a6764e07b337cae1c866471222f91f646f7e77bdcc3a770126e6a86e81b.
Структурный валидатор и scoring взяты из закреплённого исходника через AST. Источник scoring SHA256bbbdded5e9bdd04c2434769e87d7f6963ee75f6717ba475c4919a758a9703248.
Архивные исходы SHA256bb056b3e297b93cb5e28238895b5e2501b698811582bceb2fa3a9eef80a7e72d.

5. ПОСЛЕДНЕЕ ДОПОЛНЕНИЕ b27dd2d: ДНЕВНОЙ КОНТЕКСТ
Последняя версия отчёта заменила четырёхгрупповую гипотезу на два состояния по знаку доходности за 90 завершённых дней. Старое предложение four-cell сохранено только как история; его не следует запускать параллельно с новым как очередной перебор.
В опубликованном описательном анализе EMA34-down:115 событий, E1−prior TP−0.00057672 / SL−0.00039955; EMA34-up:83 события, TP+0.00788393 / SL+0.00431742.
Однако дневное состояние связано с календарём: отрицательных/положительных90d запросов F1=31/33, F2=10/57, F3=67/0. Это не независимое доказательство причинной роли тренда. В F2 обе EMA-группы хуже prior по TP; дневной фон не объясняет весь провал.
Под старым строгим разделением историй минимальная условная библиотека в F1 —2 события. С prior-mass32 локальный вес только2/34=5.9%. Это проверенная доступность, не результат обученной модели.
90-дневный знак не является разметкой полного цикла100–200 дней. В699днях всего3.5–7 номинальных интервалов такой длины; это арифметика, не число реальных независимых законченных волн.198H1 событий не создают198 независимых длинных циклов.

6. СУЩЕСТВЕННОЕ МЕТОДОЛОГИЧЕСКОЕ ОГРАНИЧЕНИЕ
Нынешний strict-disjoint контракт требует label_end исторического примера раньше самой ранней даты, используемой текущим признаком. Для EMA, зависящей от seed и всей последующей истории, это обнуляет библиотеку. Для90/180дневных признаков исключается большой объём законно известного прошлого.
Это следствие выбранного более сильного ограничения, а не доказательство утечки будущего. В моментt прошлый исход, завершившийся доt, известен, даже если его цены входят в текущее окно признаков. При этом наблюдения остаются зависимыми.
Для задачи реального прогнозирования рекомендован отдельный явно названный CAUSAL_WALK_FORWARD контракт:
label_end <= fit_cutoff <= decision_time;
каждый исторический признак построен только из собственного прошлого;
current features используют только закрытые/опубликованные кdecision_time данные;
scaler, калибровка и параметры обучены только на допустимом прошлом;
query target начинается послеdecision/entry и недоступен предиктору;
расписаниеrefit/index updates фиксируется заранее.
Такой новый контракт допускает общие уже известные исторические цены. Он не разрешает рандомное перемешивание train/test, использование будущего D1-close, незрелых меток, будущих экстремумов/длительности цикла или оценочных исходов для подбора параметров.
Старый E1 нельзя задним числом объявлять выполненным по новому контракту. Все новые методы и baselines сравнивать на одинаковой библиотеке нового режима. Старый строгий вариант сохранить и явно показать изменение доступного support. Зависимость учитывать календарными/эпизодными оценками; для100–200дневных циклов короткий14/28дневный bootstrap недостаточен.
Это не установленная причина отрицательной ошибки старого E1. Это конкретная методологическая развилка, которую нужно исправить в следующем исследовании длинного контекста, прежде чем выбирать90 дней только ради прохождения прежнего purge.

7. РЕКОМЕНДАЦИЯ
Приоритет: устранить контракты → проверить восстановление известного синтетического сигнала → проверить способность Astra находить более полезные аналоги при тех же данных и численном преобразовании исходов → связать прогноз с конкретными кандидатами входа исходной BTC-системы.
Предпочтительная роль Astra: распознавание структуры и переупорядочивание кандидатов без просмотра их будущих исходов. Вероятности и TP/SL затем вычисляются программой по общей взвешенной библиотеке прошлых путей.
Самостоятельное придумывание 27 вероятностных чисел моделью уже проверено в малой диагностике; простая смена модели не дала выигрыша.
Полный новый поиск по 699 дням здесь не выполнен: опубликованный архив позволяет воспроизвести ограниченные GPT-пакеты, но не заменяет полный закреплённый prepared minute dataset для всех прошлых путей. Следующее задание рассчитано на рабочую среду Codex с этим набором.
3TP/SL надо оценивать как последовательность исполнения. Full72h adverse touch не равен stopout после частичных TP. Успех квантильного прогноза не равен снижению просадки до 30–50%.
Не переносить модель сразу в торговлю; сначала сравнить её решения на тех же кандидатах и по тем же правилам исполнения с исходной BTC-системой. SOL имеет смысл добавлять после проверки BTC.
