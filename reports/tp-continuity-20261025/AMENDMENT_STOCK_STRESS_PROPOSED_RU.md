# Уточнение TP continuity: native stress и один дополнительный слот

**PROPOSED / НЕ СОГЛАСОВАНО.** Этот документ не запускает engine, не меняет продукт и не увеличивает текущие лимиты. Требуется прямое согласование владельца: меняется маршрут API fixture и общий предел физических запусков 3 → 4. Пилот и production исключены.

## Что уже произошло

Владелец утвердил исходный TP continuity протокол SHA `34d1fbd05160102dca08ac25a55c6e2e22d8584f04171899384bba2729f7fff4`: до 3 engineering fixtures и до 3 свежих prefix после успешных gates. Учтены 2 FAILED fixture; активных процессов 0; один существующий слот HOLD. Prefix 0/3. Старые бюджеты не переносятся.

Первый engine остановился до данных из-за неверной финальной сортировки buffer. Второй выполнил настоящие BTC/SOL входы, SOL relief и BTC debt, но fixture не вызвала modify после изменения ожидаемой аллокации. Это ошибки проверочного кода, а не доказательство stock несовместимости. Обе попытки остаются FAILED, их исходники, реальные return codes и native snapshots неизменны. Торговые 83 runtime-файла byte-identical source `763d985617abd7a7afef5eec13912303983d8837`; fixture-only HEAD `258f6ba5655de6d2c9c3fb4d081e16e576f12767` не является product patch.

Read-only review `F1-final-slot-reachability-review.json` SHA `44daecaedd3d67cef80daa9d0fbbd2ec0638dcd37aa24cd27529714d6c18a9ff` выявил ещё одну проблему сценария. На прежнем submit-маршруте обязательный valid marketable modify не достигается: resize выполняется при bid100, а после последующих TP fills оставшиеся quantities уже совпадают с frozen allocation. Обычный TP fill и reject неверного total не заменяют эту проверку. Последний слот не расходуется на заранее неполный тест.

## Предлагаемый порядок

1. До нового engine зафиксировать таблицу всех обязательных наблюдений: реальный trigger, stock API/очерёдность, native event, положительный assertion и STOP при отсутствии наблюдения. Отдельно заранее описать, как все product-сценарии следующего пункта помещаются в один будущий engine. Нет убедительного плана покрытия — STOP без расхода.
2. **Physical3: один stock API stress, без product patch.** В fixture через публичный `submit_order(order, position_id=...)` привязать три TP к **фактически существующей native BTC позиции**, прочитанной из cache после настоящего entry fill. Это явно новый тестовый маршрут, не production parity и не разрешение менять linkage в продукте. Никакого выдуманного parent, OCO, position, cash, fill, ACK, cache mutation или engine patch.
3. Начальные TP: прежние IDs владельцев уровней, цены101/102/103, native allocation212/212/576 лотов при BTC1. Настоящий SOL relief2.5 и единственный исходный cap.750; BTC debt только `max(0, actualheld-cap)`, без дополнительных cut. На фактическом reallocation trigger явно вызвать уже имеющуюся ограниченную same-OID коррекцию. Настоящие auto-generated Updated и actor ACK различаются по causal trace.
4. При bid100 проверить stock auto-resize после debt и восстановление frozen159/159/432. Затем реальный partial TP0 .050 при свежей глубине; total любого valid modify = nativefilled + desiredleaves. Отдельный настоящий invalid-total reject ниже filled не считается valid marketable modify.
5. Подать реальную native quote с bid104 и достаточной свежей глубиной. После fill одного TP stock может автоматически изменить оставшиеся связанные TP; callback correction той же заявки должна пройти public modify при уже исполнимой неизменной цене. Требуются **положительные фактические наблюдения valid marketable modify / native Updated / native TradeID fill той же исправленной заявки после Updated и до возврата public modify**, с проверкой pre-fill entitlement и реально доступной свежей глубины. Простого обычного fill или возможности исполнения недостаточно; отсутствие этого фактического вложенного исполнения = NOT_PROVEN. Порядок обхода native cache не предполагается; отсутствие нужного пути = NOT_PROVEN, не PASS. Все реальные fills проверяются по frozen entitlement до любого clamp/reallocation.
6. Проверять точную аллокацию на каждой потенциально исполнимой границе, включая nested typed/generic callbacks и возврат команды; фиксировать raw callback entry отдельно. Старые ACKed leaves могут доказывать наличие защиты, но не правильность quantities. Недоступное наблюдение, исполнимая неверная аллокация, отсутствие обязательного TP, reverse/extra cut, неточная ownership или неограниченная рекурсия — STOP. Конечная сходимость и OS0 этого не отменяют. Нормальный PASS требует real flat/orders0 и actual STOPPED → DISPOSED.
7. **Только после actual F1 PASS и независимого принятия доказательств** — узкий product patch в isolated canonical VPS worktree. Сохранить исходный product submit/linkage, BTC core/R2 LEGACY_Q, цены/веса/quantization TP, SOL signals/cuts/rearm и A0 original right. Разделить increases и protective TP; учитывать actual held residual debt и native ACK/remaining levels/current generation. Никакого принудительного присоединения product TP к position ради результата stress fixture. Один focused implementation pass и один consolidated correction по независимому money review.
8. **Physical4: максимум один integrated product fixture**, только после source freeze/engine-free проверок/независимого review/root GO. В одном engine, без account reset и скрытых дополнительных constructors, доказать всю оставшуюся семантику: paired debt/непрерывные required TP и consumed TP3; обычный TP до debt; partial/modify/reject/UNKNOWN; debt IOC race/flat/late fills/no reverse; cap/no closed-BTC refund; A0 одна переподача только исходного права. Сценарии должны быть заранее конкретизированы. Если существенное покрытие не помещается или не достигается — STOP, prefix не запускать.
