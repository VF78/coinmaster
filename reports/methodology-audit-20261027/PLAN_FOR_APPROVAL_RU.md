## Цели и порядок решения

1. Доказать исполнимость realTP и допустимого trueSOL hedge без изменения пилота/production.
2. Найти допустимую full-native точку: originalS0 profit retention≥70%, coherent-event и settled DD≤50%, zero liquidation, полная cash/fees/funding сверка.

4. После допустимости максимизировать TOTAL, устойчивость к costs/execution и простоту. Компенсирующая взвешенная сумма ROI−λDD не позволяет нарушить hard gate.

## C. Экономический эксперимент с разделёнными причинами

Предлагаемые пять экономических ячеек, не пять уже разрешённых запусков:

| Ячейка | BTC | SOL | Зачем |
|---|---|---|---|
| P0 | Точный legacy E4 | Точный старый overlay | Контроль compounding, диагностический; не претендент на truehedge |
| P1 | Только realTP-дельта, остальные E4 BTC правила сохранены | Тот же old overlay | Отделить TP-эффект и взаимодействие с ранним капиталом |
| P2 | Те же realTP BTC | OFF | Цена отсутствующей SOL alpha, базовая BTC экономика |
| P3 | Те же realTP BTC | Новый conditional portfolio-risk hedge | Основной кандидат |
| P4 | Те же realTP BTC | OFF, BTC trim по сопоставимому risk criterion | Проверить, создаёт ли SOL пользу сверх простого снижения BTC риска |

P0/P1 — исследовательские диагностические контроли, намеренно не выполняющие новые требования. Их хороший результат не объявляется победителем. Old alpha не включается скрыто в P3. P2−P0 не изолирует TP; P1−P0 изолирует TP policy при фиксированном old-overlay code, включая эндогенное изменение капитала. P3−P2 — policy effect всего нового hedge на собственном chronological capital; его нельзя вывести суммой приращений на frozen BTC trace.

Сначала использовать сохранённую ячейку только при доказанной идентичности source/config/data/clock/execution/метрик и полноте нужных snapshots. Иначе нужен зарегистрированный fresh matched control в будущем согласованном бюджете. Нельзя незаметно смешивать legacy и explicit-child admission. Не запускать P0 заново только ради воспроизводства известной цифры.

Порядок после engineering: сверка P0→P1 и решение о TP-дельте; затем P2/P4/P3. Ранняя отсечка по нарушениям защиты, cash, liquidation и уже достигнутому globalDD. Низкий промежуточный TOTAL сам по себе не доказывает провал full. Все positive/negative episodes заранее выбираются по существующим данным; это механизм-screen, не OOS.

Отчёт один: связанный путь equity/peak/DD; net cash bridge BTC/SOL/fees/funding; BTC gross/filled/pending exposures; lost/released valid rights; turnover/время hedge; effect на ранний капитал и будущие BTC sizes. Графики рядом показывают money result и нарушения исполнения. Ни current rawtestcount, ни SOL standalone PnL не заменяют этот отчёт.

Gate C: P3 должен дать экономически существенное и объяснимое улучшение по risk/cost/росту относительно P2 и риск-сопоставимого P4; прибыль не создаётся oracle timing, funding omission или favorable fill assumptions. Не требовать гарантированного P3 доминирования во всех окнах: сравнивать заранее определённые joint criteria и Pareto frontier. Если P3 систематически хуже P4 после расходов либо ранняя капитализация не имеет нового причинного источника, закрыть семейство до массового параметрического поиска. Результат prefix не обещает70/90% full; локальные thresholds фиксируются до просмотра нового результата, без старого необоснованного2x как замены главной цели.

## D. Подбор после доказанного механизма

Не более двух заранее сформулированных policy families и≤6 независимых скаляров в первой кампании. Сначала фиксированные опорные точки по экономическому смыслу и causal scenarios; затем последовательный constrained BO только при достаточном числе сопоставимых точек. При маленьком бюджете простые опорные точки полезнее GP-инфраструктуры. Полный grid/RL/новый alpha model в этот этап не входят.

Недопустимые по cash/TP/liquidation/данным варианты отмечаются infeasible, а не получают искусственную нулевую прибыль. Следующий тест выбирается по ожидаемому устранению важной неопределённости/улучшению допустимой границы на единицу полной стоимости (включая модели/переделки), а не по красивой прошлой equity curve. Prefix→full ranking предварительно проверяется по существующим сопоставимым вариантам; при слабой связи prefix используется только для механизма/ограничений.

70%/DD50 — промежуточная full historical точка; после неё параметрический ресурс идёт на90% без ослабления DD. До70% не выдавать наблюдаемую локальную DD победу за обоснование расширения. Для final shortlist — одинаковые costs/funding, native partialfills/latency/ликвидность stress, coherent event и settledDD. Не менять benchmarkBASEfees; неблагоприятные costs оформлять отдельными stress cases.

Счётчики на кампанию: сначала точный совокупный cap по готовому протоколу, включая controls/failures/robustness; переходы внутри cap по заранее объявленным gates, без просьбы расширять после каждого harness bug. После исчерпания либо установленного structuralNO_GO — завершение, не автоматическое новое имя семейства. Нельзя честно назначить достаточный full budget до GateA и выбора конечной области.

## E. Проверка устойчивости и конечный результат

Финальный полный native run нужен хотя бы потому, что compounding и globalDD не выводятся из набора локальных побед. Финансовый PASS требует обоих DD≤50% на зафиксированной частоте, полного cash/fees/signedfunding, zero liquidation, действительной TP continuity и нормального завершения positions/orders/debt. Отдельно показать модельную чувствительность к synthetic L1/depth и costs; не обещать venue/intraminute guarantee.

Rolling-origin development checks: параметры/нормализация/пороги доступны строго до решения; embargo определяется фактическим перекрытием labels/held trades, а не произвольным числом дней. Перезапуски независимых окон для robustness не выдавать за один compounding wealth path; continuous chronological replay основной для абсолютного TOTAL.

2024–2026 уже просмотрен. Любой новый split — post-selection robustness, не настоящий freshOOS. Честная независимая проверка потребует ранее не использованных доступных данных либо последующего isolated research forward stream после отдельного разрешения. Пилот/production для этого не используется. Нельзя по двум годам обещать вероятность будущего DD30–50 или сохранения90% прибыли.
