4. C0 — OLD_SOL_BTC_OPEN_ONLY: ОДИН ПОЛНЫЙ КОНТРОЛЬ

Исходная S0 с единственным изменением жизненного цикла старого SOL:
  • новые SOL increases разрешены только при actual BTC qty !=0; проверка и при создании intent, и перед submission;
  • при BTC-flat отменить pending SOL increases, затем полностью закрыть actual SOL штатным mandatory executor; late fills учесть и закрыть;
  • при BTC reversal/REGIME соблюдать исходное закрытие группы до нового открытия;
  • остальные z-entry/размеры/права/выходы SOL оставить исходными.
Не уменьшать существующий SOL при каждом BTC TP в C0: это отдельное изменение, которого в этом контроле нет. Отсутствие episode не заменять проверкой actual BTC, и наоборот.

C0 показывает цену отказа от SOL после закрытия BTC. Его отрицательный ROI сам по себе не блокирует H4: новый сигнал может иметь другую экономику. H4 сравнивать и с C0, и с S0. H4-C0 меняет сигнал, размер и выходы вместе; эта разность не изолирует вклад одной EMA. В этом цикле проверяется полная новая политика; компонентную причинность не приписывать ей без отдельной проверки. Календарь BTC может измениться при более раннем освобождении группы — это экономический эффект, а не автоматический parity bug.

Обязательный общий lifecycle C0/H4: исходный on_fill(BTC_REDUCE) сам не завершает Episode при btc_open_qty=0. При подтверждённом финальном BTC-flat, до продолжения decision pipeline, инвалидировать все неиспользованные/отложенные SOL-increase rights и pending H4 activation, заблокировать increases, отменить принадлежащие группе queued opens и native opening orders. Terminal receipts и late fills продолжать учитывать; поздний SOL fill закрыть. Явно arm _group_close_reconciliation_pending и завершить группу через штатный _reconcile_group_flat -> domain.on_group_flat только после actual flat и terminal всех её orders/owned queues. 5.2. Данные и сигнал

UTC-бары [00,04),[04,08),...; только полностью закрытые бары. На сравнительном периоде агрегировать SOL close из исходных pinned execution candles; показатель не менять источник после результатов. EMA_L(t)=a*C(t)+(1-a)*EMA_L(t-1), a=2/(L+1), seed=первый close общего warmup.
До начала сравнения взять одинаковые 730 законченных 4h-баров для всех L. Если их нет, получить только недостающий indicator warmup из того же Bybit linear инструмента существующим загрузчиком. Проверить overlap с исходной 1m-агрегацией минимум за сутки. Сохранить raw/hash/границы; execution S0 не заменять. Без достаточных причинных данных — BLOCKED_DATA конкретной ветки, не синтетический warmup.

sol_side=+1 при C>EMA, иначе -1; равенство=short как у BTC.
eligible = actual BTC qty !=0 AND sol_side == -actual BTC side.
Сигнал действует как состояние последнего доступного полного 4h-бара. Не требовать нового пересечения EMA после открытия BTC: уже существующее противоположное состояние тоже допускает вход.
Пересматривать eligible при новом закрытом 4h-баре и подтверждённых BTC fills/flat/reversal. Будущий BTC сигнал/план/неисполненный parent не считается позицией.

Входить только в сторону собственного SOL-сигнала, которая одновременно противоположна actual BTC. При одинаковых направлениях — SOL flat/выход. Не делать unconditional direction override. При BTC-flat standalone SOL запрещён; неизбежную задержку выхода по частичной ликвидности протоколировать, не маскировать мгновенным flat.

5.3. Размер: ограниченный рыночный фактор, без старой пирамиды SOL

H4 заменяет старый SOL-overlay целиком. Старые z-adds/права/timeout/выходы не должны управлять H4-инвентарём. Один экономический владелец SOL, один native executor, одно фактическое netting-положение. Не накладывать H4 поверх полного старого SOL-бюджета.

При новой активации хеджа использовать последнюю принятую причинную daily beta270 из исходного feature pipeline:
  beta0 = Cov(r_SOL, r_BTC)/Var(r_BTC), 270 daily log returns.
Это SOL-on-BTC, не обратная регрессия и не 720h beta из split_cover.
Если beta0 не конечна/<=0 либо цены/данные недоступны — не открывать, записать причину. Не подставлять beta=1 и не подбирать clamp.

По текущим принятым mark-ценам на активации PB0,PS0:
  quantity_ratio r0 = gamma * PB0/(beta0*PS0)
  Q_SOL_target = floor_to_SOL_lot(r0 * abs(actual_Q_BTC))
  SOL side = -actual BTC side.
При активации это N_SOL=gamma*N_BTC/beta0. Gamma=1 нейтрализует оценённый BTC-фактор на старте, не гарантирует минимальную дисперсию или защиту хвоста.

Заморозить beta0/PB0/PS0/r0 на активацию. Target пересчитывать только от реальных изменений BTC quantity. Не увеличивать SOL из-за роста цены, equity, изменения beta или нового daily bar. Рыночное факторное покрытие после активации может дрейфовать — измерять его, не называть gamma неизменным фактическим покрытием.

BTC entry/second-leg actual fill может повысить target в пределах действующей активации. BTC TP/reduction немедленно снижает target: отменить превышающие pending increases, дождаться terminal ACK, учесть late fills, фактически закрыть SOL сверх нового target. Старый объём не должен воскреснуть новым child. Q планового BTC, TP-credit и исходный gross H не использовать вместо actual remaining BTC.

5.4. Исполнение, срок набора и выход

Использовать существующие native admission, округление, маржу, риск-приоритеты и settlement. Порядок приоритетов: обязательные закрытия/ликвидация -> исходные BTC ordinary/TP и ранее принятый BTC split -> SOL reduction -> новый H4 increase. Не обходить отказ по доступной марже и не создавать отдельный кредитный бюджет.

При synthetic quote capacity 1000 SOL нельзя считать весь target исполненным одним IOC. Один активный child на instrument; следующий child только после terminal receipt предыдущего и на новой quote, с актуальным оставшимся target и действующим eligible. На одном quote не создавать бесконечные повторные fills или новую ликвидность. Native partial/cancel/reject — фактический результат, не полный fill.

Для набора H4 зафиксировать один срок 4h от активации. По expiry отменить ненабранные increases; уже исполненный остаток продолжает жить по правилам выхода. Expiry при равенстве времени имеет приоритет перед новым increase. Частичный fill/timeout/reject не создаёт новую активацию и не обнуляет 4h. При изменении target вниз во время набора всегда действует новый меньший target.

Событие новой активации — настоящий переход eligible false->true либо новый фактический BTC-cycle. Зафиксировать activation_ts, beta0/цены/r0 и deadline=activation_ts+4h при этом событии. Если предыдущий SOL-exit/отмены ещё не terminal, сохранить pending activation, но opens запрещены. После полного завершения старого выхода проверить текущие eligible/BTC-cycle и исходный deadline: войти можно только до него, используя замороженный r0 и актуальное actual_Q_BTC. Смена сигнала/cycle аннулирует pending activation. ACK/ожидание старого выхода не перезапускают 4h; новый таймер без нового события не появляется.
Во время непрерывно eligible состояния после expiry не восстанавливать недобранный target. Не увеличивать SOL после собственного сокращения из-за price/equity drift. При позднем BTC increase после expiry новый increase SOL также запрещён до новой активации.

Полный выход SOL: собственная EMA стала не противоположной BTC, BTC стал flat, BTC меняет сторону, исходное обязательное group close или конец теста. Отменить opens, штатно закрывать actual remaining с учётом ACK/late fills; обязательный выход не отменять ради нового сигнала. После завершения повторно оценить текущие причинные условия.
В этой первой H4-итерации нет самостоятельных SOL 3TP/SL, pyramiding и z/14d timeout. BTC 3TP/SL/trail не менять. При собственном SOL выходе не создавать новый BTC TP-credit или права старого overlay.

Регистрировать фактический time-to-first-fill, time-to-50%-target, time-to-terminal, недобор/причины, factor coverage, exposure до каждого trough. Если старый target отменён, время до 50% нового меньшего target не выдавать за своевременный набор первоначального хеджа.

5.5. Диагностическое разделение хеджа и SOL-alpha

При r_SOL = beta0*r_BTC + residual и стороне BTC s:
  pnl_pair ~= s*(N_BTC-beta0*N_SOL)*r_BTC - s*N_SOL*residual - pair_costs.
Добавка относительно того же фиксированного BTC без SOL:
  delta_pnl_SOL ~= -s*N_SOL*(beta0*r_BTC+residual) - incremental_costs.
Для всех H4-сигналов показать факторную и остаточную составляющие на сохранённом пути, а также matched-beta BTC-reduction reference с той же временной маской. Это fixed-state диагностика, НЕ самостоятельный native-контроль/TOTAL и НЕ обязательный положительный gate.
Не путать N_BTC/beta с minimum-variance hedge: последний N_BTC*Cov(B,S)/Var(S). Не запускать дополнительный covariance-optimizer.

6. B — BTC_REGIME_REENTRY_BAND_05: ОДИН РЕЦЕПТ ДЛЯ ПИЛЫ

Идея: исходный сигнал прекращает старую позицию сразу, но слабое пересечение EMA не обязано немедленно открывать полную обратную позицию.

1) Все исходные REGIME-exits исполнять без задержки. Не ждать подтверждения, продолжая держать старую сторону.
2) При фактическом закрытии группы по REGIME и terminal статусах её ордеров поставить WAIT_REGIME_REENTRY до исходного автоматического вызова _advance_current_day().
3) Пока нет episode, перед новым _domain.decide проверять последний принятый полностью закрытый BTC daily bar:
     new_side = +1 if close>EMA34 else -1
     разрешить новый вход, если new_side*(close-EMA34) >= 0.5*ATR14.
4) Если условие уже выполнено на текущем принятом баре, разрешить исходный same-session restart; не вводить обязательное ожидание ещё суток. Если нет — остаться flat до нового допустимого daily bar. При смене EMA-side в ожидании использовать новую сторону, не старый отложенный сигнал.
5) После допуска весь исходный S0 entry pipeline использует текущий капитал/цены/admission. До первого подтверждённого BTC entry fill latch сохраняется. После terminal rejection/cancellation с нулевым исполнением любая новая попытка снова проверяет band по текущему принятому daily bar; одно создание intent не снимает gate. Первый actual fill снимает latch, дальнейший split сопровождается исходным S0. Не добавлять повторы поверх существующего lifecycle и не оставлять phantom episode для обхода gate.
6) Начальное открытие, повторные входы после TP/TRAIL и выходы существующей позиции дополнительной полосой не ограничивать. Во время ожидания нет будущих BTC/SOL-прав.
7) Каталог wave-TP продолжает строиться по исходной raw daily EMA34, а не по новой последовательности разрешённых сделок.

ATR14 — настоящий Wilder ATR по полностью закрытым дневным OHLC:
  TR_t=max(H_t-L_t,abs(H_t-C_(t-1)),abs(L_t-C_(t-1)))
  первый ATR=mean первых 14 доступных TR с предыдущим close;
  далее ATR_t=(13*ATR_(t-1)+TR_t)/14.
Использовать общий исходный daily warmup S0; сохранить его границы и seed. EMA34 — в точности исходная инициализация, не новая библиотечная версия. При отсутствии проверенных OHLC получить только недостающий indicator warmup того же инструмента. Не заменять ATR стандартным отклонением/close-range и не менять seed/период после результата. При неизвестном/non-finite/неположительном ATR новый B-entry запрещён с явной причиной; исходный REGIME-exit выполняется.

Один параметр 0.5 ATR, без оптимизации ADX/ER/числа переключений/порогов по эпизодам. Band=0 нужен лишь как короткая проверка исходных entry-permissions, не отдельный полный backtest.

Это отличается от B1 (задержка всех входов) и R2 (два дня подтверждения). Сильное пересечение может допустить вход сразу. Ограничение: первый убыток до REGIME и избыточный уже открытый SOL этот модуль сам по себе не исправляет.

8. КОРОТКАЯ ПРОВЕРКА ДО ПОЛНЫХ ЗАПУСКОВ

Один причинный feature/event cache для шести H4 и B. Только завершённые данные, availability и native event ordering; одинаковый timestamp сам по себе не разрешает читать ещё не доставленный бар. Сделка — на следующем допустимом событии native executor после сигнала. Не присваивать close-trigger гарантированному fill и не менять общую latency/matching model.

Он НЕ требует положительного равновзвешенного среднего price-proxy. Не отбрасывать страховку только потому, что она стоит денег. После механически корректного precheck выполнить полные C0/H4/B, даже если дешёвая оценка неоднозначна.

Нужные короткие regression/integration cases, без новой тестовой платформы:
  • default-OFF сохраняет исходный S0; band=0 сохраняет permissions и same-session REGIME reentry;
  • закрытый 4h SOL бар не прочитан раньше времени и не попал в legacy 1h-handler;
  • BTC flat/same-side SOL signal -> нет нового SOL increase; late fill после cancel учтён;
  • BTC TP во время частичного SOL entry уменьшает target, старые leaves не восстанавливаются;
  • один quote/terminal ACK не порождает повторного использования ликвидности;

  • H4 не управляется одновременно старыми z/timeout exit; C0 сохраняет старую логику кроме BTC-flat;

Проверять реальные ошибки, не писать десятки тестов, повторяющих формулы реализации.

9. БЮДЖЕТ NATIVE И ПОРЯДОК ВЫБОРА

Основные восемь 24-месячных runs: C0(1), H4(6), B(1). Сначала C0 и первый H4 E34/G0.5; после проверки их реальных событий — B и оставшиеся пять H4. Исправление технического дефекта не означает подбор экономических параметров; все прерванные/исправленные попытки учитывать в журнале ресурсов.

До трёх дополнительных полных запусков:
  P0: только если runtime/архитектура отличаются от проверенного S0 и нет attested economic parity, один исходный S0 на этом runtime до сравнения кандидатов. В прежнем проверенном окружении использовать сохранённый точный S0, не повторять.
  X: одна комбинация выбранного H4 и B, если обе ветки технически валидны и имеют реальные действия. Не тестировать остальные комбинации.
  R: один fresh repeat максимального-TOTAL кандидата, реально прошедшего 50/90, если такой найден. Зафиксировать source/config/input hashes до повтора, проверить economics/fills по прежнему repeat contract; допуски после результата не расширять.

Итого не более 11 полных native runs, обычно 8–10; никаких скрытых Optuna/trials. Каждый физически выполненный полный 24-месячный запуск расходует слот, включая INVALID и полный повтор после исправления. Прерванные короткие попытки учитывать отдельно по ресурсам, без бесконечных retries. Если из-за технического дефекта слотов недостаточно, закончить доступные независимые проверки и пометить оставшиеся NOT_RUN. Если P0 обнаружил несогласованность S0, сначала локализовать её, не сравнивать несопоставимые результаты и не отключать проверку.
Один native engine одновременно на M2 Pro 16 GB; существующий установленный runtime, без переустановки/upgrade ради задания. Подготовку/cache делать один раз, сохранять результат каждого run для возобновления. После первого измерить реальные CPU/wall/RSS; не обещать время по старому VPS CPU. 11. СТАТУС РЕЗУЛЬТАТА И ГРАНИЦА ЭТОГО ЦИКЛА

PASS_50_90: одновременно global settled DD<=50% и profit retention>=90%, валидное исполнение; окончательно подтверждён после R.
MODULE_ONLY: доказанный локальный полезный эффект, общая цель не выполнена. Указать цену в TOTAL и оставшийся механизм просадки; не называть победителем.
NO_GO: проверенный рецепт/семейство не проходит цель.
NOT_RUN/BLOCKED/UNKNOWN различать. Сбой данных/ресурсов не равен экономическому NO_GO.

Не отвергать всю идею SOL по шести вариантам и не объявлять её работающей по одному proxy. Вывод касается этих рецептов на этой истории. EMA13/34/89 — недостаточно плотная сетка для заявления о широком устойчивом плато.

История многократно использована. Новое разбиение 2024–2026 не делает её независимым OOS; не использовать слово OOS без доказанного ранее неиспользованного периода. После отбора заморозить модель/код и указать, какой следующий нетронутый период доступен. Paper/live в эту задачу не входит.
Существующий benchmark остаётся NOT_FAITHFUL_DIAGNOSTIC: 1m CLOSE synthetic quotes, ограниченная модель ликвидности, неподтверждённая историческая применимость margin/liquidation. Это ограничение всех сравнений, не повод менять simulator одному кандидату или обещать торговую доходность.

Третий механизм только в backlog: сверка daily-close wave-MFE с причинно достижимым post-entry intraday MFE для TP. Не внедрять сейчас: потребуется одинаковая полная intraday-предыстория исходного wave lookback. Нельзя поднять частоту только после начала теста, укоротить историю кандидату, удалить настоящие нулевые волны или одновременно подобрать SL.
